# Independent Validation Review — FAQ-Layout / FAQ-Quantum-Mapper

> **Status.** This review documents findings at the time of audit. The actionable issues it
> raised were subsequently addressed (hardcoded benchmark output paths fixed, README/report
> tables regenerated from the canonical `benchmark_eval_results.json` dataset, ablation claims
> and "continuous-cost" terminology corrected, pipeline default aligned to 5-start, and data
> provenance documented). Re-run the audit steps below against the current state to confirm.

*Scope: verify the repository's central claims about a Quadratic Assignment Problem (QAP)
pre-placement pass that "preconditions" Qiskit SABRE / PyTKET / MQT-QMAP quantum routers.*

**Overall verdict: the methodology is mostly reasonable and the *means* in the headline
tables are internally consistent, but several headline claims are not reproducible from the
repository's own archived data, key ablation claims conflate the things they say they isolate,
and the repository contains multiple mutually-inconsistent datasets. The project cannot, as
shipped, be regenerated by running its own benchmark scripts.**

---

## 1. Environment / reproducibility check (important context)

- Python available is `3.14.7`; `scipy`/`numpy`/`pytest` are installed.
- `qiskit`, `pytket`, `mqt.qmap`, `mqt.bench` are **NOT installed** (they are the runtime
  deps declared in `pyproject.toml`). Full reproduction was therefore not possible here.
- `benchmark_eval.py`, `benchmark_ablations.py` and `benchmark_rigorous.py` **hard-code their
  output paths** to `/home/karthikg/.gemini/antigravity/scratch/qap_quantum_compiler/…` — a
  personal scratch directory, not the repository. So running the README's own instructions
  (`python3 benchmark_eval.py`) does **not** regenerate the committed
  `benchmark_eval_results.json` / `benchmark_ablation_results.json` /
  `benchmark_rigorous_results.json`; those files were produced elsewhere and merely committed.
  This is a fundamental reproducibility defect (and the `/.gemini/antigravity/` prefix indicates
  the artifacts came from an external AI scratch environment).

The pure-`numpy`/`scipy` solver (Module C) **was** executed directly and validated:
- Sinkhorn–Knopp returns a valid doubly-stochastic matrix (row/col sums = 1).
- 2-opt refinement is a true local search: it never increases cost and terminates with no
  improving single swap remaining.
- `scipy.optimize.quadratic_assignment(method='faq')` returns a **discrete permutation**
  (`res.col_ind`), and `res.fun` **equals the discrete QAP cost of that permutation**
  (verified: `res.fun == sum(A*B[col][:,col])`).

## 2. Correctness of the core solver code (Modules A–E, pipeline)

- **QAP formulation** (README eq. 1) matches the code: `Tr(Aᵀ P B Pᵀ) = Σ A[i,j]·B[perm(i),perm(j)]`,
  with A zero-padded when N < M. The implementation of `compute_qap_cost` is correct.
- Module A builds a time-decayed interaction matrix from DAG layers (correct for the stated
  intent); Module B builds directed shortest-path (fidelity-weighted) distances; Module E is a
  standard greedy subgraph-extraction + greedy mapper. These are reasonable engineering
  heuristics.
- **Terminology defect.** The project repeatedly calls the pre-2-opt value a **"continuous FAQ
  cost"** from a "continuous relaxation over the Birkhoff polytope" (README Table 3; Module C
  docstrings/`faq_continuous_cost`). FAQ in SciPy returns a *permutation* and `res.fun` is the
  *discrete* cost of that permutation (verified above). There is no continuous objective value
  in `res.fun`. So the "raw continuous FAQ cost" vs "discrete 2-opt polished cost" framing in
  the headline contribution-isolation table is inaccurate terminology — both numbers are
  discrete permutation costs. The real, defensible statement is that 2-opt locally refines the
  permutation that FAQ returns.

## 3. Are the README headline numbers reproducible?

Cross-checked every cell of README Tables 1 and 2 against (a) `benchmark_eval_results.json`
and (b) the archived per-seed log `benchmark_eval_raw_seeds.json` (which the README cites as
authoritative).

- **Means: all match** the archived data exactly (e.g. Grover N=10 IBM FAQ+TKET 4840.5,
  QFT N=20 213.6, Rigetti VQE50 1.1, …, verified to 1 decimal). All success counts are 20/20.
- **FAQ + PyTKET uncertainty figures** match the stored 95% CIs.
- **SABRE-default and FAQ+SABRE uncertainty figures do NOT match the archived data.** Examples:
  QFT20 SABRE-default stored σ≈7.1 / CI≈3.4, README prints "±14.8"; QRAM SABRE-default
  stored CI≈1.0, README prints "±1.8"; Ripple IBM SABRE-default has σ=0 (deterministic) in the
  archive yet README prints "±0.4". So the SABRE columns in the README came from a *different*
  run than the file the README says archives them.

Conclusion: headline *means* and the FAQ+PyTKET CI are reproducible; the README's
SABRE-column spread figures are not reproducible from the committed data.

## 4. Ablation "contribution isolation" (Table 3) — claims are conflated / unsupported

The cost figures (166.51, 91.86, 156.41, 86.99, 122.12, 88.31, 53.17, 35.72) match
`benchmark_ablation_results.json`. But the interpretation column over-claims:

- **"Gaussian noise reduces continuous FAQ cost by 26.7% (166.51 → 122.12)"** compares a
  *single barycenter start* (166.51) against the *best of 5 Gaussian starts* (122.12). It
  conflates the multi-start gain with the Gaussian-perturbation gain. Against the proper random
  multi-start baseline (best-of-5 = 156.41) the reduction is ~21.9%, not 26.7%.
- **"Discrete 2-opt polish reduces QAP cost by 47.0% ((166.51−88.31)/166.51)"** compares the
  *barycenter, no-2-opt* config (166.51) against the *Gaussian multi-start WITH 2-opt* config
  (88.31). That removes the multi-start **and** the Gaussian scheme at the same time as the
  2-opt, so it does **not** isolate the 2-opt contribution. (The cleaner matched comparison —
  barycenter single start with vs. without 2-opt — would be 166.51 → 91.86 ≈ 44.8%, which is
  even different from the stated 47%.)
- **The "Downstream SWAPs" column is not reproducible.** `benchmark_ablations.py` performs
  **no routing at all** — it only computes QAP costs. The "downstream SWAPs" figures
  (4533.0 / 3824.0 / 3766.8 / 5420.0 / 4022.0) do not come from routing each ablation config.
  Only 4533.0 and 3766.8 appear anywhere, and they are values for a *Grover N=10 tket* run on a
  **different, 115-qubit topology** (`benchmark_rigorous_results.json`) than the 127-qubit
  `FakeBrisbane` used for the ablation costs in the same table. 3824.0 / 5420.0 / 4022.0 are not
  traceable to any config-routed measurement at all.
- The Table-3 story is additionally self-undermining: the Random multi-start config has a
  **lower** polished cost (86.99) than the praised Gaussian config (88.31), and the undirected
  config has the *lowest* cost (35.72) yet the *highest* claimed swaps (4022). Those two
  contradictions undercut the thesis that "lower QAP cost ⇒ fewer downstream SWAPs," on which
  the method's value rests.

## 5. Selective reporting / hidden contradictions

`benchmark_eval.py` evaluates 20 tasks, but README Tables 1–2 show a curated subset. Rows
omitted from the README contradict the promotional reading:

- IBM Grover **N=8**: FAQ+TKET 1039.0 vs PyTKET-default 851.0 (**worse**); N=12: FAQ+TKET
  15669 vs 12610 (**~24% worse**, +3059 SWAPs). README only shows N=10, the one size where
  FAQ+TKET wins.
- IBM VQE(20/50), GHZ50: FAQ+TKET ≥ PyTKET-default (0.6 vs 0, 12.4 vs 12, 6 vs 0) — all worse
  or tied, none shown.
- FAQ+SABRE is worse than SABRE-default on essentially every standard benchmark (Grover, QFT,
  QAOA, VQE, GHZ); it only "wins" on two near-zero hand-crafted holdouts (QRAM, ripple).
- The README's own trade-off criterion recommends FAQ "for large-scale search circuits
  (Grover)," which the omitted Grover N=12 result directly contradicts.

These omissions do not make the reported means false, but they make the headline narrative
("FAQ pre-placement improves routers") materially overstated.

## 6. The repository contains multiple mutually-inconsistent datasets

`reports/complete_benchmark_table.md` ("All 36 Test Cases") uses yet *another* set of numbers
and *another* methodology (K=5 seeds, df=4, **SABRE `optimization_level=3`**, a 115-qubit
Heavy-Hex topology) that contradict the README (K=20, `optimization_level=1`, 127-qubit /
80-qubit), e.g. QFT20 IBM = 225.6±19.4 there vs 225.0 in the README; VQE50 reductions of
"−92.7%", GHZ "−99.3%", and a claim of "PyTKET default 100% crash" that does not appear in the
current README. `team_summary.md`/`walkthrough.md` duplicate the README, but
`complete_benchmark_table.md` — a "report" the project ships — contradicts it. There are also
many overlapping result files (`benchmark_results.json`, `benchmark_statistical_results.json`,
`benchmark_2_results.json`, `benchmark_rigorous_results.json`, `benchmark_new_circuits_results.json`,
`benchmark_tket_all_results.json`, `benchmark_fgea_results.json`) that do not agree. A single,
reproducible, internally-consistent dataset is absent.

## 7. Minor consistency issues

- README/ablation header call it a "6-way ablation suite," but only 5 configs exist.
- README and Module C describe a "5-start Gaussian" method, but the shipped
  `FAQCompilerPipeline` defaults to `num_faq_starts=3`.
- Ablation "Ours" Gaussian uses `σ=0.08/M` single-scale for all 5 starts, which does **not**
  match the real `AdaptiveFAQSolver(start_mode='gaussian')` schedule (1 barycenter + 2 small
  `0.05/M` + 2 medium `0.15/M`), so the ablation is not testing the shipped method.
- Module-count framing "Modules A–E" matches the files; the ion-trap/all-to-all rows were
  removed from the README after peer review but remain stale in `complete_benchmark_table.md`.

## 8. What is genuinely valid

- The core heuristic is a legitimate, if standard, idea: pre-placement via an approximate QAP
  solved with SciPy FAQ + 2-opt polish; the pure-numpy math is correct and well-tested.
- On the Rigetti-grid tasks and a few IBM tasks, FAQ-seeded PyTKET does consistently beat
  PyTKET's native `GraphPlacement` (e.g. VQE50 −91.5%, QFT20 −24.8% on IBM). Those means are
  internally consistent and match the archived logs.
- The README is more honest than the older report: it discloses hardware-snapshot scope
  (no live hardware), heuristic non-convexity, router over-constraining, and reports that
  FAQ+SABRE often *hurts* and PyTKET-default is often already optimal on easy circuits.

## Bottom line

A defensible kernel exists (QAP pre-placement + 2-opt), and the *reported means* that back the
main FAQ+PyTKET result are internally consistent with archived per-seed logs. However, as a
claim of a validated, reproducible scientific result it currently fails on several grounds:
(1) benchmark scripts cannot regenerate their own committed outputs (hard-coded external paths);
(2) README SABRE-column uncertainties are not reproducible from the archived data;
(3) Table-3 ablation "isolations" conflate the factors they claim to isolate, mislabel discrete
FAQ costs as "continuous relaxation costs," and include a "downstream SWAPs" column that is not
measured by any ablation script and stitched from a different topology/circuit;
(4) the headline tables are curated to omit several tasks where FAQ is substantially worse
(notably IBM Grover N=8/N=12, VQE, GHZ), so the central improvement claim is overstated;
(5) the repo ships mutually inconsistent "complete" benchmark datasets.
